# Authorization Code Flow with PKCE

## What is PKCE?

PKCE stands for **Proof Key for Code Exchange**. It's an extension to the OAuth 2.0 authorization code flow (defined in RFC 7636) that protects against authorization code interception attacks. It was originally designed for mobile/native apps that can't keep a client secret confidential, but it's now recommended for all clients, including web apps and single-page applications.

## Why is it necessary?

In the basic authorization code flow, the authorization server returns an authorization code to the client through a browser redirect. If someone can intercept that redirect (for example a malicious app on a mobile device, or through leaked logs/history), they could try to exchange the code for tokens. PKCE prevents this by requiring the client to send a secret proof at the token exchange step that only the legitimate client knows.

## The key values

- **code_verifier**: a random, high-entropy string generated by the client and kept secret.
- **code_challenge**: derived from the verifier. With the recommended method, it's the SHA256 hash of the verifier, base64url-encoded.
- **code_challenge_method**: usually `S256` (SHA256). There is also a `plain` method but S256 is recommended.

## Step by step

1. **Generate the verifier and challenge.** The client creates a random `code_verifier` and computes `code_challenge = base64url(SHA256(code_verifier))`.

2. **Authorization request.** The client redirects the user's browser to the authorization endpoint, including:
   - `response_type=code`
   - `client_id`
   - `redirect_uri`
   - `scope`
   - `state`
   - `code_challenge`
   - `code_challenge_method=S256`

   Example:
   ```
   GET /authorize?response_type=code&client_id=myapp
       &redirect_uri=https://myapp/callback
       &scope=openid profile
       &state=abc
       &code_challenge=XXXX
       &code_challenge_method=S256
   ```

3. **User authenticates.** The user logs in and grants consent at the authorization server.

4. **Authorization code returned.** The server redirects back to the client's `redirect_uri` with a `code` and the `state`:
   ```
   GET /callback?code=AUTH_CODE&state=abc
   ```

5. **Token exchange.** The client makes a back-channel POST to the token endpoint with:
   - `grant_type=authorization_code`
   - `code`
   - `redirect_uri`
   - `client_id`
   - `code_verifier` (the original random string)

   ```
   POST /token
   grant_type=authorization_code&code=AUTH_CODE
       &redirect_uri=https://myapp/callback
       &client_id=myapp
       &code_verifier=ORIGINAL_VERIFIER
   ```

6. **Server validates.** The authorization server hashes the received `code_verifier` and compares it against the `code_challenge` it stored earlier. If they match, it issues the tokens (ID token, access token, and optionally a refresh token).

## Why it stops interception

Only the `code_challenge` (a hash) is ever sent in the front-channel authorization request. The `code_verifier` is only sent in the back-channel token request. An attacker who steals the authorization code cannot exchange it because they don't have the `code_verifier`, and they cannot compute it from the challenge since SHA256 is a one-way function.

## Practical note for web apps

Most modern OAuth/OIDC client libraries handle PKCE for you automatically. When you configure your OpenID Connect middleware you typically just enable it and the library generates the verifier and challenge, stores the verifier, and sends it during the token exchange. You rarely need to implement the hashing yourself.
